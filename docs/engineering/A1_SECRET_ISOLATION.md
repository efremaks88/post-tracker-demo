# A1 — изоляция проектных реквизитов доступа

Дата проверки: 15.10.2026. Этап выполнен без подключения к production и без изменения схемы базы данных.

## Найденные места

Проектные реквизиты исторически хранятся в JSONB-поле `projects.dossier`. Основная структура — массив `dossier.accesses` с названием записи, логином и паролем. Досье до A1 целиком проходило через модель проектов, общий ответ `GET /api/data`, состояние React и обратную массовую запись `PUT /api/data`.

На клиенте тот же объект мог оказаться:

- в оперативном состоянии приложения;
- в резервной копии `localStorage` текущего пользователя;
- в JSON-файле «Скачать мои изменения»;
- в полях просмотра и редактирования на вкладке проекта «Доступы и ссылки».

Глобальный поиск не читал `dossier.accesses` напрямую, но наличие реквизитов в общем клиентском состоянии делало их доступными любому клиентскому коду. XLS-аналитика реквизиты не экспортировала. Аудит операций проекта записывал идентификатор и служебные сведения, а не содержимое досье. LDAP-пароль используется только во время запроса входа и к проектным реквизитам не относится.

Значения реквизитов при инвентаризации не выводились в терминал, отчёты или логи.

## Что изменено

Добавлена единая серверная граница `lib/project-secrets.js`:

- перед выдачей проектов удаляются поля с именами, характерными для логинов, паролей, токенов и ключей;
- элементы `dossier.accesses` превращаются в безопасные метаданные: название и признак наличия сохранённых реквизитов;
- общий и точечный API отклоняют попытку записать новое значение реквизита;
- при обычном сохранении проекта прежние закрытые поля и весь прежний массив `accesses` объединяются с безопасной правкой и остаются в исходной строке базы.

Клиент повторяет фильтрацию как второй рубеж перед загрузкой в состояние, отправкой на сервер, записью в `localStorage` и JSON-экспортом. Старые локальные резервные копии очищаются при следующем открытии. Поля просмотра и редактирования реквизитов заменены информационной карточкой со статусом. Пути и обычные ссылки остаются редактируемыми.

Исходные значения в базе не удалялись, не переносились, не перезаписывались и не ротировались. Нового API просмотра закрытых значений нет.

## Проверки

Автоматические тесты используют только искусственные маркеры и проверяют:

- отсутствие значений в `GET /api/data` у ролей admin, lead, manager, editor и viewer;
- сохранность закрытых полей в базе после массовой и точечной безопасной правки;
- отказ общего API принимать новые логины, пароли или токены;
- отсутствие маркеров в аудите, состоянии клиента, запросе сохранения, локальной копии и JSON-экспорте;
- отсутствие поля пароля в карточке проекта.

Фильтрация основана на структуре и именах полей. Произвольный секрет, вручную вставленный в обычное текстовое описание или заметку без обозначения поля, нельзя надёжно распознать автоматически. Такие тексты не относятся к найденной структуре хранения и требуют отдельной проверки содержания перед внешней демонстрацией.

## Предлагаемая безопасная миграция

Миграцию следует выполнять отдельным согласованным этапом:

1. Выбрать менеджер паролей и создать хранилище с группами доступа по проектам.
2. Сформировать инвентарный список только с идентификаторами проектов и названиями записей, без значений.
3. Выполнить одноразовый перенос серверным скриптом напрямую из базы в хранилище. Скрипт не должен печатать значения и обязан вести журнал только идентификаторов и результата операции.
4. Проверить доступ владельцев проектов и резервное восстановление хранилища.
5. Заменить записи в трекере безопасными ссылками или идентификаторами элементов хранилища.
6. После отдельного подтверждения ротировать реквизиты, затем удалить старые значения из `projects.dossier` и проверить резервные копии согласно сроку хранения.

Шаги 3–6 в A1 не выполнялись. Они требуют выбора хранилища, правил доступа и отдельного подтверждения владельца продукта.
